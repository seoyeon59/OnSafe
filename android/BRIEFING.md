# 2부. 백엔드에게 물어볼 것

## ① 실시간 영상 — 어느 방식으로 갈지 정해야 한다 (가장 급함)

### 지금 상황 정리

어제 백엔드에서 보내준 조사 문서로 확실해졌다. **내가 파악한 것과 결론이 같다.**

- 예전에 "실시간 영상" 설계가 있었는데 **이미 폐기됐다** (PR #23, 8월 5일)
- 폐기 이유: 영상을 쏴줄 카메라 장치가 **한 번도 만들어진 적이 없어서** 서버 쪽 통로만 있고
  들어올 데이터가 영원히 없는 상태였음
- 지금 서버로 가는 건 영상이 아니라 **관절 좌표(숫자)**뿐이다. 영상 자체가 서버에 없다
- 즉 **백엔드·안드로이드 양쪽 다 완전 미착수**

> 쉽게 말하면: 지금 구조에서 보호자가 볼 수 있는 "지금 이 순간의 영상"이라는 데이터가
> 애초에 존재하지 않는다. 낙상이 감지됐을 때 폰이 저장해둔 mp4를 나중에 올리는 것만 있다.

### 백엔드가 제시한 3가지 안 — 각각 무슨 뜻인가

#### A안. WebRTC P2P — "두 폰을 직접 연결"

보호자 폰과 카메라 폰을 **서버를 거치지 않고 직접** 영상으로 연결하는 방식.
영상통화(페이스톡)와 같은 기술이다. 서버는 "너희 둘 연결해봐" 하고 소개만 시켜준다.

| | |
|---|---|
| 좋은 점 | 화질·속도가 가장 좋다. 서버가 영상을 안 다루니 서버 비용도 거의 안 든다. 추가 장비 불필요 |
| 나쁜 점 | **구현 난이도가 셋 중 압도적으로 높다.** 안드로이드에 WebRTC를 붙여야 하고, 백엔드에 중개(시그널링) 서버가 필요하고, 공유기 뒤에 있는 폰끼리 연결시키려면 TURN 서버라는 것도 따로 띄워야 한다 |
| 내 판단 | 남은 기간에 이걸 새로 배워서 완성하는 건 현실적으로 어렵다고 본다 |

#### B안. 서버 중계 — "폰이 서버로 올리고, 서버가 보호자에게 뿌린다"

카메라 폰이 화면을 조금씩 서버로 올리고, 서버가 그걸 받아서 보호자 폰으로 넘겨주는 방식.
폐기된 옛 구조를 되살리되, 영상을 올리는 쪽만 IP 카메라에서 안드로이드 폰으로 바꾸는 것.

| | |
|---|---|
| 좋은 점 | 추가 장비가 필요 없다. 설계가 한 번 있었던 구조라 백엔드가 뭘 만들지 감이 있다 |
| 나쁜 점 | 백엔드가 지운 인프라를 다시 만들어야 한다. 영상이 전부 서버를 거치니 서버 부하·비용이 크다. 카메라 폰은 **관절 인식 + 영상 인코딩 + 업로드를 동시에** 해야 해서 발열과 배터리 소모가 심해진다 |
| 내 판단 | 화질을 크게 낮추면(예: 1~2초에 한 장씩 사진처럼) 현실적으로 가능해 보인다. 완전한 동영상은 무리 |

#### C안. IP 카메라 구매 — "전용 카메라를 따로 산다"

가정용 IP 카메라(홈캠)를 사서 설치하고, 그 카메라가 주는 주소를 앱이 받아서 재생만 하는 방식.

| | |
|---|---|
| 좋은 점 | **앱 작업이 제일 적다.** 주소를 받아서 재생하기만 하면 된다. 서버도 기존 API를 거의 그대로 쓴다 |
| 나쁜 점 | 장비를 사야 한다. 그리고 **"낡은 폰을 재활용한다"는 프로젝트 컨셉과 정면으로 충돌한다** |
| 큰 문제 | 낙상 감지는 안드로이드 폰이 하는데 영상은 IP캠이 보여준다면, **같은 장면을 두 대가 동시에 찍고 있어야 한다.** 설치가 이상해지고, 왜 폰이 필요한지 설명이 안 된다 |

### 내 의견 (물어볼 때 같이 얘기할 것)

**실시간 영상 보기를 이번 범위에서 빼는 것도 선택지로 올려보고 싶다.**

이유는 이렇다.

- 낙상 시 4분짜리 영상을 저장하고 보여주는 기능은 **이미 동작한다** (Storage만 열리면 확인 가능)
- 보호자 입장에서 정말 필요한 건 "평소에 계속 지켜보는 것"보다 "사고가 났을 때 확인하는 것"에
  가깝다고 생각한다
- 셋 중 어느 안을 골라도 백엔드 신규 작업 + 안드로이드 신규 작업이 동시에 필요한데,
  남은 기간에 다른 미완성 항목(푸시 알림 등)과 병행이 가능한지 확인이 필요하다

**꼭 해야 한다면 B안의 축소판**(1~2초에 한 장씩 캡처해서 올리는 방식)을 제안한다.
"실시간 영상"이라기보다 "실시간 화면 확인"에 가깝지만, 구현 난이도 대비 가장 현실적이다.

## ② Firebase Storage 요금제, 누가 언제 올리나

낙상 영상이 만들어지는 것까지는 확인했는데 **저장할 공간이 없어서 업로드가 실패한다.**
무료 요금제로는 안 되고 결제 수단 등록이 필요하다. 프로젝트 소유자만 할 수 있다.

이것 없이는 영상 재생·다운로드를 테스트할 방법이 아예 없다.

## ③ 보호자가 자기 계정을 따로 갖는 방식인가

서버에 **보호자 연결 기능이 완성돼 있다** (코드 발급 → 코드 입력 → 연결 → 해제).
Redis 처리에 요청 제한까지 붙어 있는, 제대로 만든 기능이다.

그런데 우리 앱은 **같은 계정으로 두 폰에 로그인**하는 방식이라 이 기능을 하나도 안 쓴다.

| 결론 | 앱에 필요한 작업 |
|---|---|
| 지금처럼 같은 계정 | 없음. 서버의 guardian 기능은 미사용으로 정리 |
| 보호자가 별도 계정 | **화면 2개 신규** (코드 발급 화면, 코드 입력 화면) |

> 지금 방식이 고장 난 건 아니다. 같은 계정이면 알림이 한 인박스에 쌓이고 두 폰이 같은 걸
> 읽으니 정상 동작한다. 다만 서버는 별도 계정 구조도 상정하고 있어서 확인이 필요하다.

## ④ 낙상 오탐 시 쿨다운을 푸는 API를 만들어줄 수 있나

한 번 위험이 감지되면 서버가 **6시간 동안 다음 감지를 막는다.** 설치나 테스트 중에 오탐이
한 번 나면 그 6시간 동안 진짜 낙상도 못 잡는다.

앱에 "잘못된 감지입니다" 버튼을 넣고 싶은데, **쿨다운을 푸는 기능이 서버에 없어서
앱만으로는 못 만든다.**

## ⑤ JWT 키를 32자로 맞춰줄 수 있나

테스트 중에 **로그인은 되는데 카메라만 연결이 안 되는** 현상이 있었다. 원인은 키 길이였다.

Kotlin 서버는 키가 48자 이상이면 다른 방식으로 서명하는데, Python 서버는 그 방식을 못 읽는다.
오류도 안 뜨고 조용히 실패한다. **운영 배포에서 이게 걸리면 원인 찾기가 정말 어렵다.**

## ⑥ 운영 서버 주소는 언제 나오나

지금 앱에는 `api.neulbom.com`이라는 임시값이 들어 있다. 실제 주소가 나와야 배포용 빌드를
만들 수 있다.

## ⑦ 촬영이 끝났다는 걸 서버가 알려줄 수 있나 (급하진 않음)

지금은 서버에 마지막 점수가 계속 남아 있어서, 앱이 "값이 15초간 안 바뀌면 끝난 거겠지" 하고
추측하고 있다.

이러면 **정상 종료인지 카메라 폰이 고장 난 건지 구분이 안 된다.** 후자면 보호자에게
알려줘야 하는 상황인데 똑같아 보인다. 당장 급하진 않지만 알고는 계셨으면 한다.

# 3부. 팀 전체가 정해야 할 것

## ⑴ 알림 목록 보관 기간 — 택 1

화면 문구는 "최근 7일"인데 실제로는 사고이력과 같은 데이터를 그대로 쓰고 있고, 7일로 자르는
로직이 없다.

### 확인 결과 — 알림 전용 API는 따로 있다

| 구분 | 사고이력 | 알림 |
|---|---|---|
| 저장 위치 | `fall_logs` | `notifications` (별도) |
| 조회 API | `GET /api/fall-logs/{userId}` | `GET /api/notifications/{userId}` |
| 읽음 처리 | `PATCH .../confirm` | `PATCH .../{알림ID}/read` |
| 내용 | 낙상 기록 원본 | 보호자에게 전달된 알림 사본 |

같은 낙상이라도 **알림은 본인과 보호자에게 사본이 각각 쌓인다.** 성격이 다른 데이터인데
지금은 사고이력으로 대신하고 있어서, 서버의 읽음 상태와 앱 화면이 따로 논다.

추가로 알아낸 것: **알림 조회 API에는 기간 제한이 아예 없다.** 최근 50건을 내려준다.
설정상 보관 기간은 30일 고정인데, 알림을 실제로 지우는 스케줄러는 확인되지 않았다.

| 안 | 내용 | 작업량 |
|---|---|---|
| ① | 화면 문구를 30일로 변경 | 한 줄 |
| ② | 앱에서 7일로 필터링 | 작음 |
| ③ | **알림 전용 API로 교체** | 중간 — 내가 진행 가능 |

> ③이 원래 맞는 방향. 다만 기간 문구는 ①·②와 별개로 여전히 정해야 한다.

## ⑵ 주소 입력 안내 문구를 넣을지

회원가입·개인정보 수정의 주소가 **가입자 본인 주소인지 피보호자 주소인지** 안내가 없다.
119 신고 시 쓰일 주소라면 피보호자 주소여야 맞다.

→ "피보호자가 계신 주소를 입력해주세요" 같은 문구를 넣을지 결정 필요.

---

## ⑶ 영상이 아직 안 만들어졌을 때의 안내

낙상 영상은 **감지 시점 앞뒤를 모두 담기 때문에 감지 후 약 2분이 지나야 완성된다.**
그 전에 사고이력에서 영상 보기를 누르면 지금은 그냥 없는 것처럼 보인다.

→ "영상을 준비 중입니다 (약 2분 소요)" 같은 안내가 필요하다. 문구와 표시 방식 결정 필요.

---

## ⑷ 메인 화면의 피보호자 이름 / 기기 ID

홈 상단의 이름과 기기 ID가 지금은 고정 문구다.

- **기기 ID**: 보호자 폰은 카메라 폰의 ID를 알 수 없다. → 이 칸을 **연결 상태 표시로 대체**하는
  방향을 제안한다
- **이름**: 메인에 이름이 꼭 필요한지부터 논의 필요. 넣는다면 누구 이름인지(보호자 본인 /
  피보호자) 정해야 한다

---

## ⑸ 낙상 알림 모달에 "잘못된 감지입니다" 버튼

오탐 시 6시간 쿨다운을 풀 수단이 필요하다. 남용 방지를 위해 횟수 제한을 두는 것까지 함께 검토.

> **백엔드 작업이 선행돼야 한다** (2부 ④번과 같은 건).
> 서버에 쿨다운 해제 API가 생겨야 앱에서 버튼을 만들 수 있다.

---

## ⑹ 카메라 모드에서 홈 버튼으로 나갔을 때

지금은 홈으로 나가도 촬영이 계속된다. 사용자가 종료된 줄 알 수 있다.

| 안 | 내용 | 문제 |
|---|---|---|
| A | 나가면 자동 종료 | 직관적이지만 **무인 감시 목적과 충돌** |
| B | 상태바에 "촬영 중" 상시 표시 | 사용자가 항상 인지 가능. 포그라운드 서비스 구현 필요 |
| C | 나갈 때 "백그라운드에서 계속 촬영할까요?" 안내 | 매번 물으면 번거로움 |

> 무인 감시가 목적이면 A는 어렵다. B가 정석이지만 구현이 들어간다.
> 개인적으로는 **B**를 권한다 — 안드로이드 정책상으로도 백그라운드 카메라는 상태바 알림을
> 띄우는 게 정석이고, 사용자 오해도 확실히 해소된다.

# 4부. 참고 — "주의는 안 뜨고 위험만 뜬다"에 대해

테스트 중 궁금했던 것. **코드에는 문제 없다.** 확인 결과는 이렇다.

## 서버는 주의도 정상 처리한다

점수 구간은 이렇게 나뉜다.

```
0 ~ 50      정상
50 초과 ~ 75  주의    ← 알림 저장됨, 쿨다운 5분
75 초과      위험    ← 알림 저장됨, 쿨다운 6시간
```

서버 코드를 보면 주의 구간에서도 기록을 남기고 "주의 수준 감지" 알림을 만든다.
앱의 알림 목록에도 노란색 항목으로 표시되게 되어 있다.

## 그런데 왜 안 보였나 — 이유 3가지

**1. 위험이 한 번 뜨면 15분간 점수가 안 내려간다**

서버에 "점수 바닥 유지"라는 장치가 있다. 한 번 75를 넘으면 **15분 동안 그 아래로 떨어지지
않게 붙잡는다.** 위험 상황이 잠깐 잠잠해졌다고 안심시키지 않기 위한 것이다.

→ 결과적으로 낙상 직후 15분 동안은 계속 "위험"이라 주의 구간이 아예 안 생긴다.

**2. 넘어지는 동작은 너무 빠르다**

낙상은 순식간이라 50~75 구간을 거의 안 거치고 바로 75를 넘는다. 게다가 판정은 30프레임씩
묶어서 하기 때문에, 중간 구간이 한 묶음에도 안 잡히고 지나갈 수 있다.

**3. 주의는 팝업이 없다 (이건 내가 그렇게 만들었다)**

홈 화면에 뜨는 큰 알림창은 **위험일 때만** 뜨게 되어 있다. 주의는 알림 목록에만 쌓인다.
주의마다 팝업이 뜨면 사용자가 피곤해질 것 같아서 그렇게 했다.

→ **이 부분은 팀 확인이 필요할 수 있다.** 주의도 팝업이 필요하다면 바꾸면 된다.

## 주의를 직접 확인해보려면

넘어지지 말고 **천천히 몸을 기울이거나 앉는 동작**으로 50~75 구간에 머물러야 한다.
그리고 직전에 위험이 떴다면 15분을 기다리거나 서버 쪽 기록을 지워야 한다.

# 5부. 배포 전에 반드시 처리해야 할 것 (공유만)

| 항목 | 현황 |
|---|---|
| **릴리즈 서명 키** | 없음. 배포용 빌드 자체가 생성되지 않음 |
| **ProGuard MediaPipe 규칙** | 누락. **배포 빌드에서만 낙상 감지가 안 될 수 있음** |
| 운영 서버 주소 | 임시값 |
| 약관·개인정보처리방침 URL | 비어 있음 (스토어 등록 필수 항목) |
| Firebase Storage | 미개설 |

> ProGuard 항목은 개발 빌드에서는 절대 드러나지 않는다.
> 배포 전환 후 실기기로 낙상 감지를 반드시 다시 확인해야 한다.
